## What the product is for

Turn a well-posed mathematical question into useful, inspectable evidence:
choose promising methods, try them, challenge the conclusions and change course
when evidence warrants it. Infrastructure serves this loop; infrastructure work
is not itself mathematical progress.

Five responsibilities, reusing existing components:

1. **Dossier:** exact statement, quantifiers, source, known results, unresolved goal.
2. **Strategy:** a small competing portfolio; each direction names a discriminating
   experiment and what result would make us abandon or revise it.
3. **Agents:** solver proposes; critic independently challenges; repair retains
   the failed version and addresses the actual objection. Agreement is not proof.
4. **Verification:** exact computation/replay for finite claims; argument review
   for proofs; Lean only where an appropriate formalization is feasible. These
   acceptance types must not be silently substituted for each other.
5. **Evidence/UI:** originals, provenance, scope, outcome, limitation and next
   decision visible. A failed approach can be useful evidence without solving
   the problem; a hash only identifies bytes.

## Default developer loop

Small change → syntax/type/tests → focused independent review → scoped result.
Do cheap checks before build, browser demonstrations or expensive source audits.
Use installed Node/TypeScript/test tooling. No bespoke dependency census or
per-helper operation pricing for ordinary developer verification.

`npm run research:check` is the scoped early check; `npm run research:replay`
is a known public permutation arithmetic engineering replay. Neither command
grants research authority, verifies all application code, validates a proof or
measures fresh LLM ability. They do not replace full integration/E2E checks.

The check includes the actual replay CLI as its final smoke stage. Mocked tests
and typechecking alone cannot establish that a Node entrypoint launches correctly.
Explicit ESM is used for that entrypoint; no change to the application's package
module format is needed.

## Keep the right boundaries

Developer tooling executes trusted checkout code. Do not expose it as a tool
that executes arbitrary agent-generated code. Production authentication,
authorization, resource ceilings, cancellation, source admission, independent
replay and durable evidence remain mandatory at their actual runtime boundaries.
User decisions concern target, material strategic shifts, resources and release;
routine reversible implementation checks should not require repeated approvals.

Old R3 remains failed/deferred/unaccepted with its original history and ceilings.
Its private parser/toolchain is not the default development route and is not
silently repaired or reissued. No historical evidence is deleted.

## A useful research session

Start from one exact question and at most a few live directions. For each:
prediction → discriminating test/lemma → retained result → independent check →
continue, revise or stop. An experiment should change a decision or close a
named mathematical gap. Repeatedly enlarging finite samples without such a
reason is a warning to stop, not evidence of approaching a theorem.

Measure time to first checked result, concrete gaps closed, reproducibility,
wrong conclusions caught and method changes justified by evidence. Count tests,
agent messages or audit rows separately; none is a measure of mathematical depth.

## What this correction does not claim

It is an incremental recovery of development practice, not a complete rewrite
or a claim that autonomous research is solved. A new research campaign, paid API,
formal theorem, blind benchmark or release requires its own explicit scope.

## Research run discipline, without approval ceremony

Before a run, write only the exact question, admissible output and stop condition.
Choose an approach from mathematical structure and known literature, not a fixed
sequence of tools. Ordinary local checks/repairs inside the chosen task are agent
work; do not seek human approval for every reversible step.

If an attempt fails, retain it and change the approach only with an explicit
reason. Do not swap the question, soften acceptance or count a new task name as
fresh progress. A run succeeds only when ALL its selected outputs are established;
otherwise report the exact unresolved output. Global proof, a tuple witness,
continuous tightness for one tuple and conditional family proof are different
results. Tests establish their specified controls, not the unrestricted theorem.

Infrastructure has a named defect and a smallest sufficient fix; otherwise park
it. For LRC_METHOD_VALIDATION_084, the default demonstration is two fixed cases,
exact witnesses/coverage, independent replay and deliberately wrong certificates.
No prime campaign, dependency census or historical-proof relabelling is needed.
